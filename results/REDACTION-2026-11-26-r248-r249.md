# REDACTION — 2026-11-26 — r248/r249 banks: client-subnet access lines

Law 8 event (found by the gate itself post-merge, 2026-11-26; the
leak_sweep rfc1918 pattern flagged 21 lines in pushed commit 729cf4e9).
Second occurrence of the r231de gap class (first: REDACTION-2026-11-24).

## What leaked

The three banked serve logs carried `GET /v1/models` API-server
access lines from the client LAN host `10.100.8.<client>` (7 lines
each — the last octet is redacted here exactly as the pass below
redacts it in the banks):

- `results/2026-11-26-p647-ph1-r248-lmc-mx-triage/serve.log`
- `results/2026-11-26-p647-ph2-r249-lmc-mx-interop/serve.log`
- `results/2026-11-26-p647-ph2-r249-lmc-mx-interop/run1/serve.log`

Root cause chain: (1) the r248/r249 pull scripts' law-8 redaction
block covered only the rig subnet (`10.20.3.x` → the `RIG_ADDR` /
`CLIENT_ADDR` tokens these two banks use) — the client subnet
`10.100.8.x` was missing from the pattern set even though every
P2-era bank already redacted it to `10.100.8.REDACTED`; (2) the
sweep ran at bank time BEFORE the `git add -f` of the gitignored
logs — invisible to the untracked pass (gitignore) and to the
tracked pass (not yet in the index) at that moment — and was not
re-run after the force-add, where the tracked pass would have seen
them (verified: `git grep` reads the index, so staged-but-
uncommitted files are in scope). The 11-24 note prescribed exactly
this re-run as manual discipline; it failed again — the fix below
makes the index content a gate pass of its own.

## The pass (byte-exact, the historical convention)

`perl -pi -e 's/\b10\.100\.8\.6\b/10.100.8.REDACTED/g'` — the same
byte form every P2-era banked log already carries (last-octet
redaction; the sweep's numeric-octet patterns correctly treat it as
clean). Applied to the three logs; zero raw occurrences remain
(verified per file). Post-pass state of the three banks: rig
addresses in the `RIG_ADDR` token form (from the pull scripts;
older banks use `10.20.3.REDACTED` — both forms sweep-clean), client
addresses `10.100.8.REDACTED`. Each bank's `SHA256SUMS` regenerated
post-redaction; `SHA256SUMS.rig` in the r249 bank keeps the rig-side
pre-redaction sums as pull provenance — its `serve.log` entry
differs from the local (redacted) file by design; this note is the
explanation.

## Structural fixes (same increment)

1. `tools/ar/r248_pull.sh` + `tools/ar/r249_pull.sh`: the redaction
   block gains the client-subnet pattern
   (`s/\b10\.100\.8\.\d+\b/10.100.8.REDACTED/g`) — future pulls of
   these banks cannot re-leak.
2. `tools/leak_sweep.sh`: a third pass "staged" over the INDEX
   (`git grep --cached`) — the index is the pushable-bytes truth at
   commit time, and the pass closes the miss-window where bytes are
   staged dirty and the working tree is cleaned afterwards (the
   tracked pass reads the working tree and would false-pass). The
   header now states the operational law outright: re-run after
   every `git add -f` — the untracked pass covers the pre-add
   window, the staged pass the post-add one.
