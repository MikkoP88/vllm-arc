## 2. Two real taxes (the fix targets for the directive)

### Tax A — continuation-prefill bulk dequant (kernel REFUTED as driver by p182)

The 3.3-3.7 s chunk-gap phases at 16K/32K n8. Ramp arithmetic: ~256K prompt
tokens prefilled over ~117 s ~ 2.2K tok/s prefill throughput — slow for
27B TP2 on dual B70.

Mechanism (code recon, 2026-11-14): under chunked prefill
(max_num_batched_tokens 4096) a 32K prompt = 1 first chunk + 7
continuation chunks. engine.py `_prefill_attention` dispatch: first chunk
rides raw flash-attn (format-free, fast); every continuation chunk
(q_len=4096 > `_CONTINUATION_DECODE_THRESHOLD` 128) calls
`_continuation_prefill` = **bulk `mx_dequant_cache` of the ENTIRE cached
prefix + flash over cached+chunk** — the dequant work is O(ctx^2/chunk)
per request per layer (4K+8K+...+28K = 112K token-rows per request at
32K, x 48 layers).

Kernel-level REFUTATION (p182 runs 1+2, bank deqv2A26, 2026-11-14): v1
`_mx_full_dequant` — one `num_warps=1` program per (token, head) —
measures 0.25-0.78 ms per whole-prefix call across formats at the
continuation hot range (120-248 GB/s effective; ~248 GB/s at 28K =
bandwidth-saturated). The 114K single-warp CTAs hide latency through
sheer program parallelism — the pre-v6 decode-starvation analogy did NOT
carry over. Per chunk across 48 layers the dequant contributes ~14-37 ms
= 2-4% of an observed ~1.4 s stall chunk: **the dequant is NOT the stall
driver**.

Run 2 (sane 0..125 byte domain; run 1's all-NaN gate artifact banked as
deqv2_run1_nanartifact.txt) adds the tiled-v2 verdict: bit-identical
everywhere, and a **length-split result** — v2 (T16/T32 tiles, all
winners PACKED=0) WINS 16K+ (mxfp8@16K **1.71x**, mxk8v4@28K 1.22x,
ties at the 248 GB/s ceiling) but LOSES 8K (0.49-0.69x — v1's
one-CTA-per-token parallelism is already optimal there). The K2/K3
packed lanes never win a single cell. Landing shape if pursued: hybrid
dispatch (v2 for cached_len >= ~12K, v1 below) inside
`mx_dequant_cache`; ceiling gain ~10-20 ms/chunk at 16K mxfp8 — real but
a small e2e lever (2-4% share above).

Re-attribution (working hypothesis, ctrl arbitrates): a 4K-token chunk of
27B GEMMs is ~110 TFLOP/GPU ≈ ~1 s at B70 bf16 — chunked-prefill compute
dominates the ramp on ANY KV dtype; the MX-specific share (dequant +
flash-over-cached-prefix instead of pure chunk-local flash) is tens of
ms/chunk. If the r186 ctrl ramp matches the MX ramps (2.0-2.2K tok/s),
Tax A is generic prefill throughput, out of decode-parity scope — the
parity bar then rests on Tax B.

### Tax B — e2m1 dequant ALU wall on the m4q serve path

Engine wiring (engine.py:109-135): the MTP verify batch (the dominant
decode attention) rides **v5 dot + K2 packed-fp16 dequant by default for
mxfp8 + mxk8v4** — but **mxfp4 stays on the v2 lane with the full ~18-op
f32 e2m1 chain** (join flavor, K2/K3 do not apply to v2). The freeze
rationale — "keep bit-identical numerics inside the open e2m1-V quality
investigation (r161 acceptance 0.0% at 32K)" — is **void as of r185**:
KNEE=none on cert25zb, acceptance healthy through 32K (the r168 LMC
auto-off fix was the cure).

Lever B1 (measured, ready): flip mxfp4 verify v2 -> v5. The A13 "v5 is a
0.94-1.05x wash on mxfp4" verdict PREDATES K3; with K3 the v5 m4 kernel
banks 7.618 ms vs v2's ~8.2-9.2 (r179 k3cycleA18) — ~1.1-1.2x kernel win.
Quality gates for the flip: v5's offline d<=2e-3 gate + the r185 acceptance
ladder as the e2e quality face. A/B via ARC_MXKV_VERIFY_DECODER=v5 on a
debug leg; ship as default only after the ladder re-runs clean.

Lever B2 (research): the residual e2m1 dequant itself (K4-class — cheaper
packed-domain unpack than K3's nibble->e4m3-byte map). Only if B1 leaves
m4q >1.1x off m8q at 32K after the flip.

Note the m8q lane has its own headroom: the per-row draft/decode path
(q_len==1, engine.py:698/918) uses v2 f32 dequant for ALL formats — K2
packing does not ride that lane. Tax B work should A/B the v2-lane K2/K3
port too (same constexpr plumb as v5's, per-row math stays f32 sums ->
numerics class unchanged except the dequant product rounding, which K2/K3
prove bit-identical anyway).

## 5. Final verdict + gap decomposition + telemetry-leg design

**S1 verdict: GREEN.** `ACCEPT_KNEE_PASS` on all four cells; KNEE=none
through 32K on every MX lane (the r161-era 0.0% acceptance at 32K is
fully cured — cert25zb + the r168 LMC auto-off fix). No adaptive
ARC_SPEC off-switch is warranted by this ladder.

**Decode parity: not yet at FP8 level — the gap is n1 long-context.**

- ctrl n1 ITL is FLAT across the ladder (40→43 ms, +3 over 28K ctx);
  every MX lane grows linearly (m4q 49→112, mkq 58→126, m8q 65→106).
  Per-step deltas vs ctrl at n1: m4q +9/+18/+35/+69, mkq
  +18/+26/+44/+83, m8q +25/+29/+34/+63 (4K→32K). The deltas scale with
  ctx and cluster across formats (+63..+83 at 32K) — this is the
  **attention-on-MX path** signature (dequant work ∝ cached tokens),
  not a constant aux-pipeline tax (A1/P1/F2 would be flat; the constant
  component is only the 4K-n1 residual, +9..+25 ms).
- At n8 steady state the gaps compress to 1.04–1.27× at 32K (but reach
  1.7–1.9× at 8K, where ctrl's own step is cheap) — the n8 step
  amortizes the per-row MX cost across a larger shared step.
- K/V attribution (32K n1 delta): V-side e2m1 vs e4m3 costs ~+20 ms
  (mkq +83 vs m8q +63, same K-e4m3, both v5); K-side and lane effects
  are confounded (m4q rides the v2 f32 chain, mkq/m8q ride v5) — m4q is
  nonetheless the FASTEST MX lane at n1 12K+ despite the slower lane,
  so format payload (e2m1 = half the KV bytes) still wins below ~12K.
- Tax A (continuation-prefill bulk dequant) stays refuted (2–4% of a
  stall chunk, p182/deqv2A26): the ramp parity across lanes at n8 32K
  (ctrl 1671 vs m4q 1978 ss) confirms chunked-prefill compute, not MX
  dequant, owns the ramp.
