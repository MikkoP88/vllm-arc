ROOT CAUSE — SOLVED AT SOURCE LEVEL (the G2 long-prefill engine freeze)
-----------------------------------------------------------------------------
The v3 warm gate and the engine compile DIFFERENT TRITON CACHE KEYS for
the same kernel because they pass the `softcap` scalar with different
Python types:

  warm gate   (patch_arc_xpu_warmup_gate.py:195):  softcap=0.0   float
  engine      (triton_attn.py:505-508):            None -> 0     int

Triton maps a Python float to an fp32 runtime arg ('fp32', None) and a
Python int to an i32 specialization candidate ('i32', 'D' — 0 is
div-16). The arg type is part of the kernel signature, the signature is
part of the cache key (jit.py compute_cache_key: key = specialization +
str(options)). Every kernel the warm gate compiles therefore lives in a
key space the engine never looks up, and every engine attention call
cache-misses regardless of geometry coverage.

Class-matrix proof (class_matrix.txt; 11072 traced lookups, 20 unique
cache-key classes, first-appearance per class):
  * warm gate 05:41-05:56: exactly 4 classes, ALL with softcap fp32/
    None — prefill-shaped (BLOCK_M=64, BLOCK_Q=32/8, non-3D), covering
    hd256 full+sliding and hd512 full+sliding.
  * engine init 06:01-06:14: 16 further classes, ALL with softcap
    ('i32','D') — decode/capture-shaped only (BLOCK_M=16, BLOCK_Q=8/2,
    IS_3D segmented variants + reduce_segments twins). The engine's own
    boot path never compiles a prefill-shaped class with the int-softcap
    signature.
  * first real request (probe98, 06:16:46): needs the hd256-sliding
    PREFILL class with ('i32','D') softcap — compiled NOWHERE in the
    boot. Fresh IGC compile ~288 s (+ first-launch module _init_handles)
    > the 300 s execute-model RPC watchdog (VLLM_EXECUTE_MODEL_TIMEOUT
    _SECONDS, envs.py:242) -> EngineCore dies -> HTTP 500.

This also resolves r108u's "byte-identical yet cache-missing" puzzle:
