Root cause (evidence-complete)
------------------------------
The 10/60 FULL-attention layers (hd512, no window) are bound by the
L2/HBM-bandwidth wall, structurally:
- Per call (q=8192, k=32768): 2048 programs (1024 q-blocks x 2 KV
  heads), each program re-walks its causal K/V span (~18 MB avg
  fp8)  -> ~37 GB of K/V reads per 10.8 s call = 3.4 TB/s effective
  = the L2 bandwidth class (B70 HBM is ~1.1 TB/s; the working set
  64 MB mostly fits L2). The same arithmetic reproduces every
  measurement: k98k rate drops (0.676 TF/s) exactly when the 192 MB
  K/V footprint outruns L2; time ~ 1/BLOCK_Q from M16->M64; all
  non-BLOCK_M knobs are noise.
- Why not more reuse? BLOCK_M (q rows sharing each K/V load) is
  SLM-capped at 64 by the 64x512 fp16 Q tile (+ K/V stage buffers);
  M128 cannot even launch. The (BLOCK_M x 512) fp32 accumulator
  additionally ties registers at M64 (spill exists but is secondary
  per the hd256 control).
- Upstream parity: upstream vllm HEAD (vllm/v1/attention/ops/
  triton_unified_attention.py @ f98575e, 2026-11-07) has the SAME
  acc structure (tl.zeros([BLOCK_M, HEAD_SIZE_PADDED], fp32)) and
  its newest per-band tables pin hd512 big-q prefill to (64,32,8,1)
  — i.e. upstream sits on the same wall; there is NO newer fixed
  shared component to lawfully import (radiance/line-C/line-D
  donors do not carry this file). Stock upstream config (M16
  class) would be ~5.3x WORSE than our cert12 table — the fork's
  launcher table already recovers everything config-recoverable.
- Sweep verdict: certified (64,32,8,None) is AT the ceiling —
